# LEEF (Log Event Extended Format) Samples

This directory contains log samples in **LEEF format**. LEEF (Log Event Extended Format) is a structured logging format developed by IBM QRadar that provides a standardized way to represent security events and log data from various sources.

## About LEEF

LEEF was created to address the need for a more flexible and extensible logging format compared to CEF (Common Event Format). While CEF uses a fixed header structure, LEEF provides greater flexibility in field definitions and supports more complex data structures.

### LEEF vs CEF Comparison

| Feature | LEEF | CEF |
|---------|------|-----|
| **Developer** | IBM QRadar | ArcSight (Micro Focus) |
| **Field Structure** | Key-value pairs with flexible extensions | Fixed header + extensions |
| **Delimiter** | Configurable (typically `\|` or `\t`) | Fixed pipe (`\|`) delimiter |
| **Extensibility** | Highly flexible custom fields | Limited extension fields |
| **Complexity** | More complex parsing | Simpler, more standardized |

## Understanding LEEF and Syslog

Like CEF, LEEF messages are commonly transported using the Syslog protocol. The relationship can be understood as two distinct layers:

- **Syslog** is the **transport envelope** providing metadata like Priority (`<PRI>`) headers
- **LEEF** is the **structured message payload** containing the actual event details

### Example Breakdown

Consider this sample LEEF log:

```log
<134>LEEF:2.0|IBM|QRadar|7.3.0|Authentication|src=192.168.1.100|dst=10.0.0.50|spt=12345|dpt=443|proto=TCP|act=Accept|usrName=admin|devTime=Jul 25 2025 13:00:01
```

Breaking this down:

1. **Syslog Header**: `<134>` - Priority value indicating facility and severity
2. **LEEF Message**: `LEEF:2.0|IBM|QRadar|7.3.0|Authentication|src=192.168.1.100|dst=10.0.0.50|...`

## LEEF Format Structure

### LEEF Header Format

```
LEEF:Version|Vendor|Product|Version|EventID|Delimiter|Extensions
```

**Header Fields:**
- **LEEF**: Format identifier (always "LEEF")
- **Version**: LEEF version (1.0, 2.0)
- **Vendor**: Vendor/manufacturer name
- **Product**: Product name
- **Version**: Product version
- **EventID**: Event type identifier
- **Delimiter**: Field separator character (optional in 2.0)
- **Extensions**: Key-value pairs containing event data

### LEEF Versions

#### LEEF 1.0
```
LEEF:1.0|Vendor|Product|Version|EventID|key1=value1|key2=value2|key3=value3
```

#### LEEF 2.0 (Recommended)
```
LEEF:2.0|Vendor|Product|Version|EventID|^|key1=value1^key2=value2^key3=value3
```

LEEF 2.0 improvements:
- Configurable delimiter (default: `^`)
- Better handling of special characters
- Enhanced escaping mechanisms
- Support for nested structures

## Common LEEF Fields

Standard fields frequently used in LEEF logs:

### Network Fields
- **src**: Source IP address
- **dst**: Destination IP address
- **spt**: Source port
- **dpt**: Destination port
- **proto**: Protocol (TCP, UDP, ICMP)
- **mac**: MAC address

### Security Fields
- **act**: Action taken (Accept, Deny, Block, Allow)
- **severity**: Event severity level
- **cat**: Event category
- **threat**: Threat/malware name
- **signature**: Signature ID

### User/Identity Fields
- **usrName**: Username
- **srcUserName**: Source username
- **dstUserName**: Destination username
- **realm**: Authentication realm

### Time Fields
- **devTime**: Device timestamp
- **rt**: Receipt time
- **start**: Start time
- **end**: End time

### Data Fields
- **bytesIn**: Bytes received
- **bytesOut**: Bytes sent
- **cnt**: Count/frequency
- **msg**: Message/description

## Parsing Considerations

When working with LEEF logs:

1. **Version Detection**: Identify LEEF version (1.0 vs 2.0) for proper parsing
2. **Delimiter Handling**: Extract and use the correct field delimiter
3. **Header Parsing**: Parse the fixed header fields before processing extensions
4. **Key-Value Extraction**: Split extension fields into key-value pairs
5. **Escaping**: Handle escaped characters according to LEEF specification
6. **Data Types**: Convert string values to appropriate data types
7. **Syslog Separation**: Separate syslog headers from LEEF payload when present

## Transport Methods

LEEF logs are typically:
- **Sent via Syslog** (UDP/514, TCP/514, TLS/6514)
- **Forwarded to QRadar** through various collectors
- **Streamed via TCP/HTTP** to log aggregation systems
- **Written to files** for batch processing
- **Published to message queues** for distributed processing

## LEEF Best Practices

1. **Use LEEF 2.0**: Prefer LEEF 2.0 for new implementations
2. **Consistent Delimiters**: Use consistent delimiter characters across logs
3. **Standard Fields**: Use standard field names when possible
4. **Proper Escaping**: Escape special characters according to specification
5. **Timestamp Format**: Use consistent timestamp formats (preferably ISO 8601)
6. **Field Validation**: Validate field values and data types
7. **Documentation**: Document custom fields and their meanings
