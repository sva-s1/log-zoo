# Syslog (Custom) Log Samples

This directory contains log samples that use **standard syslog protocols** but with **custom or non-opinionated message payloads**. Unlike structured formats like CEF, LEEF, or JSON, these logs follow syslog transport standards while containing free-form or application-specific message content.

## About Syslog (Custom)

Syslog serves as a universal transport mechanism for log messages, but the actual message content can vary widely depending on the source application or system. This directory focuses on logs that:

- **Follow syslog transport standards** (RFC 3164 or RFC 5424)
- **Contain custom message formats** that don't conform to established structured formats
- **Use application-specific** or vendor-specific message structures
- **Represent raw syslog output** from systems without additional formatting layers

## When to Use This Directory

Place log samples here when they:

1. **Use syslog transport** but don't fit other structured format categories
2. **Contain custom message formats** specific to particular applications or vendors
3. **Follow syslog RFC standards** for headers but have non-standardized payloads
4. **Represent raw system logs** without additional parsing or formatting
5. **Include legacy syslog formats** that predate modern structured logging

## Syslog vs Structured Formats

| Aspect | Syslog (Custom) | Structured Formats (CEF/LEEF/JSON) |
|--------|-----------------|-----------------------------------|
| **Transport** | Standard syslog (RFC 3164/5424) | Often syslog, but format-agnostic |
| **Message Format** | Free-form, application-specific | Standardized, parseable structure |
| **Parsing Complexity** | Requires custom parsing logic | Standard parsing libraries available |
| **Interoperability** | Limited to specific applications | High interoperability across tools |
| **Use Cases** | Legacy systems, custom applications | Modern SIEM, log aggregation platforms |

## RFC Standards Covered

### RFC 3164 - The BSD Syslog Protocol
- **Legacy standard** widely used in older systems
- **Simple format** with basic priority and timestamp information
- **Limited metadata** compared to modern standards
- **Widely supported** across Unix/Linux systems

### RFC 5424 - The Syslog Protocol
- **Modern standard** with enhanced capabilities
- **Structured data elements** for additional metadata
- **Improved timestamp precision** and timezone support
- **Message ID and process ID** fields for better tracking

## Common Sources

Custom syslog messages are frequently generated by:

- **Legacy Unix/Linux systems** with traditional syslog daemons
- **Network devices** (routers, switches) with basic syslog support
- **Custom applications** using standard syslog libraries
- **System services** and daemons with built-in logging
- **IoT devices** with simple syslog implementations
- **Embedded systems** with minimal logging capabilities

## Parsing Considerations

When working with custom syslog messages:

1. **RFC Identification**: Determine whether the log follows RFC 3164 or RFC 5424 format
2. **Priority Extraction**: Parse the `<PRI>` field to determine facility and severity
3. **Timestamp Parsing**: Handle different timestamp formats between RFC versions
4. **Hostname/Source**: Extract source system information from headers
5. **Message Content**: Develop custom parsing logic for application-specific payloads
6. **Character Encoding**: Handle various character encodings (UTF-8, ASCII, etc.)
7. **Line Endings**: Account for different line ending formats across systems

## Message Structure Overview

### RFC 3164 Structure
```
<PRI>TIMESTAMP HOSTNAME TAG: MESSAGE
```

### RFC 5424 Structure
```
<PRI>VERSION TIMESTAMP HOSTNAME APP-NAME PROCID MSGID [STRUCTURED-DATA] MSG
```

## Contributing

When adding new syslog samples to this directory:

1. **Identify RFC version** - Place samples in the appropriate RFC subdirectory
2. **Sanitize data** - Remove or anonymize sensitive information (hostnames, IPs, etc.)
3. **Document source** - Include information about the originating system or application
4. **Preserve format** - Maintain original syslog formatting and structure
5. **Explain custom elements** - Document any application-specific message formats
6. **Follow naming conventions** - Use descriptive filenames indicating the log source

For full guidelines on naming and contribution, please see the main [`CONTRIBUTING.md` file](../CONTRIBUTING.md) in the root of the repository.

## Best Practices

1. **Preserve Original Format**: Keep syslog messages in their original form when possible
2. **Document Custom Fields**: Explain any application-specific message structures
3. **Include Context**: Provide information about the generating system or application
4. **Timestamp Consistency**: Note timezone and timestamp format variations
5. **Facility/Severity Mapping**: Document how priority values map to actual severity levels
