# RFC 3164 - The BSD Syslog Protocol

This directory contains log samples that follow **RFC 3164**, the original BSD Syslog Protocol standard. RFC 3164 represents the traditional syslog format that has been widely used across Unix and Linux systems for decades.

## About RFC 3164

RFC 3164 was published in August 2001 and codified the existing BSD syslog practices that had been in use since the 1980s. While considered a legacy standard today, it remains widely supported and is still the default format for many systems.

### Key Characteristics

- **Simple format** with minimal structure
- **Fixed timestamp format** without timezone information
- **Limited message size** (typically 1024 bytes)
- **Basic priority encoding** using facility and severity
- **No structured data** support
- **ASCII character set** limitation

## Message Format Structure

### Complete RFC 3164 Message Format

```
<PRI>TIMESTAMP HOSTNAME TAG: MESSAGE
```

### Visual Breakdown with Brackets

```
[<PRI>][TIMESTAMP] [HOSTNAME] [TAG][:] [MESSAGE]
 │      │           │         │   │   │
 │      │           │         │   │   └─ Free-form message content
 │      │           │         │   └───── Optional colon separator
 │      │           │         └───────── Process/application identifier
 │      │           └─────────────────── Source hostname or IP
 │      └───────────────────────────────── Timestamp (MMM dd HH:mm:ss)
 └──────────────────────────────────────── Priority value <0-191>
```

### Detailed Field Breakdown

#### 1. Priority Field `<PRI>`
```
<PRI> = <Facility * 8 + Severity>
Range: <0> to <191>

Examples:
<16>  = Facility 2 (mail), Severity 0 (emergency)
<34>  = Facility 4 (security), Severity 2 (critical)
<165> = Facility 20 (local4), Severity 5 (notice)
```

#### 2. Timestamp Field
```
Format: MMM dd HH:mm:ss
Where:
  MMM = 3-letter month abbreviation (Jan, Feb, Mar, etc.)
  dd  = Day of month (01-31, space-padded for single digits)
  HH  = Hour (00-23)
  mm  = Minute (00-59)
  ss  = Second (00-59)

Examples:
Jan  1 00:00:00
Dec 25 23:59:59
Jul  4 12:30:45
```

#### 3. Hostname Field
```
Format: Hostname or IP address of the originating system

Examples:
server01
mail.example.com
192.168.1.100
web-server-prod
```

#### 4. Tag Field
```
Format: Process name, optionally followed by process ID in brackets

Examples:
sshd
kernel
httpd[1234]
postfix/smtpd[5678]
cron
```

#### 5. Message Field
```
Format: Free-form text message (application-specific)

Examples:
User root logged in from 192.168.1.50
Connection established
Failed password for invalid user admin
System startup completed
```

## Sample RFC 3164 Messages

### System Authentication
```
<38>Jan 15 10:30:45 server01 sshd[12345]: Accepted password for admin from 192.168.1.100 port 22 ssh2
```

**Breakdown:**
- `<38>` = Facility 4 (security), Severity 6 (info)
- `Jan 15 10:30:45` = Timestamp
- `server01` = Hostname
- `sshd[12345]` = Tag (SSH daemon, process ID 12345)
- `Accepted password...` = Message

### Mail System
```
<22>Dec 25 14:22:33 mail.example.com postfix/smtpd[8901]: connect from unknown[203.0.113.45]
```

**Breakdown:**
- `<22>` = Facility 2 (mail), Severity 6 (info)
- `Dec 25 14:22:33` = Timestamp
- `mail.example.com` = Hostname
- `postfix/smtpd[8901]` = Tag (Postfix SMTP daemon)
- `connect from unknown...` = Message

### Kernel Message
```
<4>Jul  4 08:15:30 firewall kernel: iptables: DROP IN=eth0 OUT= SRC=10.0.0.100 DST=192.168.1.50
```

**Breakdown:**
- `<4>` = Facility 0 (kernel), Severity 4 (warning)
- `Jul  4 08:15:30` = Timestamp (note space padding for single-digit day)
- `firewall` = Hostname
- `kernel` = Tag (kernel messages)
- `iptables: DROP...` = Message

### Web Server
```
<134>Nov 30 23:45:12 web01 httpd[2468]: 192.168.1.200 - - [30/Nov/2025:23:45:12 +0000] "GET /index.html HTTP/1.1" 200 1234
```

**Breakdown:**
- `<134>` = Facility 16 (local0), Severity 6 (info)
- `Nov 30 23:45:12` = Timestamp
- `web01` = Hostname
- `httpd[2468]` = Tag (Apache HTTP daemon)
- `192.168.1.200 - -...` = Message (Apache access log format)

## Facility and Severity Codes

### Facility Codes (0-23)
```
 0 = kernel messages          12 = NTP subsystem
 1 = user-level messages      13 = log audit
 2 = mail system              14 = log alert
 3 = system daemons           15 = clock daemon
 4 = security/authorization   16 = local use 0 (local0)
 5 = messages generated by    17 = local use 1 (local1)
     syslogd                  18 = local use 2 (local2)
 6 = line printer subsystem   19 = local use 3 (local3)
 7 = network news subsystem   20 = local use 4 (local4)
 8 = UUCP subsystem           21 = local use 5 (local5)
 9 = clock daemon             22 = local use 6 (local6)
10 = security/authorization   23 = local use 7 (local7)
11 = FTP daemon
```

### Severity Codes (0-7)
```
0 = Emergency   - System is unusable
1 = Alert       - Action must be taken immediately
2 = Critical    - Critical conditions
3 = Error       - Error conditions
4 = Warning     - Warning conditions
5 = Notice      - Normal but significant condition
6 = Info        - Informational messages
7 = Debug       - Debug-level messages
```

## Limitations of RFC 3164

1. **No Timezone Information**: Timestamps assume local time
2. **Year Ambiguity**: No year field in timestamp
3. **Limited Character Set**: ASCII only, no Unicode support
4. **Message Size**: Typically limited to 1024 bytes
5. **No Structured Data**: No standardized way to include metadata
6. **Hostname Ambiguity**: May be hostname, FQDN, or IP address
7. **Tag Inconsistency**: No standardized format for process identification

## Parsing Considerations

When parsing RFC 3164 messages:

1. **Priority Extraction**: Parse `<PRI>` to calculate facility and severity
2. **Timestamp Handling**: Assume local timezone, handle year rollover
3. **Field Separation**: Use space as delimiter, but handle variations
4. **Tag Parsing**: Extract process name and optional PID
5. **Message Content**: Everything after TAG: is the message
6. **Character Encoding**: Assume ASCII, handle non-ASCII gracefully
7. **Malformed Messages**: Handle missing fields or invalid formats

## Common Variations

Real-world RFC 3164 implementations often include variations:

- **Missing hostname**: Some implementations omit the hostname field
- **Different tag formats**: Various ways of including process IDs
- **Extended timestamps**: Some add year or timezone information
- **Non-ASCII characters**: Despite specification, some include Unicode
- **Longer messages**: Some implementations exceed 1024-byte limit

## Migration to RFC 5424

Many organizations are migrating from RFC 3164 to RFC 5424 for:
- **Structured data support**
- **Improved timestamp precision**
- **Unicode character support**
- **Better internationalization**
- **Enhanced metadata capabilities**
